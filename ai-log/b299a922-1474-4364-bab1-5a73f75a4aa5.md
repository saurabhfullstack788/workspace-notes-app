No secrets, personal data or binary files, and only standard dependencies. After that comes a 60-minute live session: walkthrough, a code review exercise and a design discussion.

## Points that are easy to get wrong

- **"A policy mistake must deny":** enable RLS *and* `FORCE ROW LEVEL SECURITY`, and only write permissive policies (no "allow all" fallback). The app must connect as a role without `BYPASSRLS` that doesn't own the tables. With Supabase, the service-role key skips RLS, so it must never be used on request paths.
- **Server-derived identity:** the user comes from a verified session or JWT. For each request, set the user context inside the transaction (`SET LOCAL` / `set_config`) so the RLS policies can read it. The workspace is always checked against the user's memberships.
- **Not revealing existence:** "forbidden" and "doesn't exist" return the same 404 everywhere, with no different error messages or timing tricks.
- **"Direct database call" edge case:** you need a way to show it, e.g. a test or script that connects as the app role with user A's context and gets 0 rows (or an RLS error) when querying workspace B.
- **"Every tenant table":** this includes the table that stores summaries and the memberships table. Policies are needed per command (`SELECT`/`INSERT`/`UPDATE`/`DELETE`, with `WITH CHECK`), so a row can't be moved into another workspace.
- **Roles enforced twice:** checked in server code and again in the RLS policies.
- **Summary safety:**
  - Validate with Zod before storing.
  - The mock fails once, then a retry succeeds or you return a clean error.
  - Note text goes inside delimiters as data, never as instructions.
  - The output is rendered as escaped text.
  - The mock can echo a note containing "ignore previous instructions" to show it doesn't change behaviour.
- **`ai-log`:** this Claude Code session is saved as a `.jsonl` file under `~/.claude/projects/...`. It has to be copied in unedited, so keep that in mind when deciding what to type in sessions. Also, this folder isn't a git repo yet.

## Decisions before we start

1. **Postgres in Docker or Supabase?** I recommend **plain Postgres in Docker**. RLS stays explicit and easy to explain (your own app role plus `current_setting('app.user_id')`), there's less setup, and there's no service-key risk. Supabase gives you built-in auth and `auth.uid()`, but it's heavier locally and hides more of what's happening.
2. **Auth:** simple email/password, with sessions in signed httpOnly cookies, and seeded users for the demo. This is enough to show the server verifying the user itself.
3. **Data access:** raw `pg` or Drizzle, with a single `withUser(userId, tx => …)` helper that every query must go through. Tests would use Vitest against the real Docker database.
